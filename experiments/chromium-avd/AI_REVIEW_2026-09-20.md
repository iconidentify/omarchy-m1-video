## Confirmed findings

### R1 — P2: a recoverable UBSan report can pass the positive test gate

**Introduced in the experiment; high confidence.** `E/test.py:88–97` compiles with `-fsanitize=address,undefined` but supplies neither `-fno-sanitize-recover=undefined` nor a fatal UBSan setting. `run([str(binary)])` accepts the positive suite solely by zero exit status. UBSan's recovering checks can diagnose undefined behavior and continue to a zero exit; this would still reach the printed PASS. The four mutation invocations separately inspect stderr (`E/test.py:122–124`), but the positive invocation does not.

Trigger: a UBSan-detectable recovering error on the positive test path which does not otherwise fail a GoogleTest assertion. Consequence: CI can present the sanitizer acceptance gate as passed despite a UBSan finding. This is a validation defect, not evidence that the selector currently has undefined behavior.

Strongest counterargument: the current job passed without an observed UBSan report. I checked the retained `logs/ci-fb175d5.log`; it does show twelve successful tests and all four mutation detections, and has no sanitizer diagnostic. That supports the observed clean run but does not repair the gate for subsequent changes.

Requested fix: make UBSan fatal for all compiled test binaries, and retain a bounded deliberate diagnostic probe so removing that setting cannot silently weaken the gate. The parent is preparing this fix and will use hosted CI; this reviewer did not run a probe locally.

**Final disposition: confirmed and resolved in `88715ec221803700aa23adf40aeeaf3db7c61af8`.** `E/test.py:88–109` now shares `-fno-sanitize-recover=undefined` between the positive tests, mutation builds, and a small signed-overflow probe. The probe must compile, emit the intended `runtime error: signed integer overflow` diagnostic, and exit with a positive nonzero status; a signal, timeout, missing diagnostic or recovering zero exit cannot pass. The exact-head hosted log executes and passes this gate, twelve tests and all four mutations. No local execution was performed by this reviewer.

### R2 — P2: prepared runtime completion precedes teardown, while existing guard “idle” omits owned holders

**Prepared-harness acceptance defect, separate from the PR's C++; high confidence.** Reviewed initial runner: `selection-candidate-prepared.py`, SHA-256 `a94e39f1d58b206eee0b675465489eaa544cb3927766237d8a0afeb7c197cbc1`. Lines 130–131 record `completed`/`passed_execution` before the `finally` block attempts Browser.close and waits/terminates/kills at lines 135–143. Cleanup only runs while the main browser PID is alive and the fallback signals target that PID.

The imported, pre-existing `/home/chrisk/src/driver-m1-candidate-20260920/tests/hwguard.py:567–591` computes final idle from `foreign_holders(final, proc.pid)`. `foreign_holders` at lines 130–139 excludes holders in the owned process group/ancestry. `_kill_group` at lines 414–435 also returns immediately if the direct runner already exited. Thus a browser child surviving the main browser/runner can remain an owned AVD holder without contradicting the recorded `idle=true`.

Trigger: an owned GPU/browser child outlives main-browser exit or incomplete cleanup. Consequence: the record can claim successful completion/idle while decoder ownership persists. The strongest counterargument is that normal Browser.close generally exits children; that expected behavior is precisely what the required final observation must establish, and the current classification excludes the counterexample.

Requested fix for this experiment: emit acceptance only after teardown and a fresh full-state check, independently of the helper's foreign-holder filter. `LinuxBackend()` with no `preflight_since` uses `journal_since(None)` and `journalctl -k -b` (`hwguard.py:197–200,251–269,85–91`). Retain the returned state and require no `state.holders`, no `state.wedged`, and no `state.faults`. `preflight(LinuxBackend())` additionally requires module/video presence and enforces these conditions at lines 373–382. A failed/unfinished cleanup remains a failed run, with no automatic retry. Preserve process-group guard coverage; do not detach the browser into an unmanaged session to simplify cleanup. The parent is preparing runner v2.

**Intermediate correction in prepared v2; runtime unexecuted.** `selection-candidate-prepared-v2.py:132–160` records playback checks as pending teardown, always obtains a fresh unfiltered whole-boot state after its teardown attempt, rejects missing module/video, any holders/busy/wedged/faults, and emits completed only when playback and that check both succeed. Exceptions escape and prevent the final completion output; the event file closes in a nested finally. Browser process-group inheritance is unchanged. SHA-256 verified: `cd757ea389c50014a57b70fd9ca02d06e46e03eceff2c231579c3c1d4a551b7a`. The original external hwguard semantics have not been fixed by this patch. V2 still allowed forced main-browser terminate/kill cleanup to result in acceptance when the full final state was idle; I raised this as a limitation on graceful-exit claims.

**Final disposition: confirmed acceptance defect, corrected by source inspection in prepared v3; runtime unexecuted.** I read the full v2-to-v3 delta and verified SHA-256 `ae8d8916cb8c4ef4c958afd8fdb99e19c031e419a3878a15a842ccd2723ab943` for `selection-candidate-prepared-v3.py`. Lines 137–158 retain the full-state gate and additionally record browser exit and require Browser.close to have been requested, exit status zero, and no forced terminate/kill. Main-browser early exit, abnormal exit, forced cleanup or failed final state cannot emit completed. ## Verified reachability and authority

1. **Actual caller and order.** `C/content/gpu/gpu_main.cc:548–570` derives accelerated-decode permission from `!gpu_prefs.disable_accelerated_video_decode` and passes `GpuPreSandboxHook` to `SandboxLinux::InitializeSandbox`. `C/gpu/ipc/service/gpu_init.cc:449–481,525–529,907–910` invokes pre-sandbox media startup before the eventual hook, for both early and ordinary GPU sandbox ordering. GPU children use the unsandboxed zygote then initialize their specialized sandbox (`C/content/browser/gpu/gpu_process_host.cc:458–474`); child feature state is initialized before GPU main (`C/content/app/content_main_runner_impl.cc:621–628,1115–1118`).
2. **Gates.** `C/content/common/gpu_pre_sandbox_hook_linux.cc:53–55,679–689` requires ARM64, USE_VAAPI, enabled accelerated decode and the default-disabled `VaapiAppleAvd` feature. The ChromeOS return at line 664 and Chromecast ARM return at line 674 occur before the new code. The new call adds only returned rules to the pre-existing policy. The selector being built into other Linux/ChromeOS configurations does not itself invoke discovery there. Ordinary page input does not feed feature configuration or selected paths.
3. **Sandbox creation.** `C/sandbox/policy/linux/sandbox_linux.cc:305–339` runs the hook before installing GPU seccomp. The hook starts the broker at `C/content/common/gpu_pre_sandbox_hook_linux.cc:716–726`. `StartBrokerProcess` owns the permission vector in its config, forks the broker and creates the client (`sandbox_linux.cc:546–564`; `broker_process.cc:61–106`). Paths are copied/owned, not pointers into the selector's temporary vectors. The broker gets its own command-limited seccomp policy (`sandbox_linux.cc:124–153`; `bpf_broker_policy_linux.cc`).
4. **Real dispatch.** Generic Linux ARM64 uses `GpuProcessPolicy`, not the ChromeOS ARM policy (`C/sandbox/policy/linux/sandbox_seccomp_bpf_linux.cc:121–143`). That policy routes relevant filesystem calls through the broker (`bpf_gpu_policy_linux.cc:122–127`). `CommandSetForGPU` already enables ACCESS, OPEN and STAT; READLINK remains ChromeOS-only (`gpu_pre_sandbox_hook_linux.cc:613–626`). ARM64 openat/newfstatat are recognized (`broker_process.cc:113–181`); the dispatcher requires AT_FDCWD and permits the supported stat flags (`syscall_dispatcher.cc:35–52,109–116,193–195`). Baseline statx handling returns ENOSYS for STATX_BASIC_STATS so glibc can use the old stat path (`baseline_policy.cc:315–324`). No new syscall class was introduced.
5. **Host enforcement.** The client's optional fast check is not the authority boundary: `BrokerHost::OpenFileForIPC` and `StatFileForIPC` recheck the command set and stored policy before the actual syscall (`broker_host.cc:134–164,260–310`). O_CLOEXEC is handled through MSG_CMSG_CLOEXEC and removed before the primitive predicate (`broker_client.cc:294–332`; `broker_command.cc:37–48`). The tests intentionally exercise this predicate boundary, not the entire IPC mechanism.

## Selector, permissions, and dismissed concerns

**D1, dismissed: arbitrary paths or cameras become selected.** `E/overlay/content/common/apple_avd_gpu_permissions_linux.cc:55–115,168–205` constructs names only from bounded indices: renderD128–191, video0–63, media0–63. Native lstat rejects final symlinks, non-character files and non-root owners (119–129). The selector requires sysfs `dev` to equal the observed major/minor, canonical platform topology, DRM major 226/render minor matching its name, V4L major 81, exact canonical `asahi`/`avd` driver paths and exact NUL-delimited M1 compatible tokens. Media must be a direct child of the already validated video physical device and have a distinct device identity. Dynamic media major is allowed deliberately. Missing/invalid candidates receive no rules; only one validated render/video/media set is accepted. Unrelated invalid/non-AVD cameras may coexist without acquiring added permissions.

**D2, dismissed: broad or recursive metadata access.** The mapping selects nonrecursive ReadWrite, ReadOnly, and StatOnlyWithIntermediateDirs factories (`apple_avd_gpu_broker_linux.h:11–28`). Real `BrokerFilePermission` factories and predicates enforce those choices (`broker_file_permission.h:50–57,80–87,155–163`; `.cc:77–92,136–227,258–278`). The stat-only path authorizes itself and component-boundary ancestors, including `/`; it does not authorize directory listing/open, children, sibling device numbers or arbitrary prefix matches. Read-only uevent rejects write and O_RDONLY|O_TRUNC. RW devices permit ordinary read/write/access/stat, but not creation; standard status/open flags and write-side O_TRUNC remain Chromium semantics rather than an invented “only O_RDWR” contract.

**D3, dismissed as a patch regression: existing generic permissions and ioctl exposure.** AddStandardGpuPermissions remains additive and includes card0–9, Nvidia paths and its pre-existing /dev/shm grant (`gpu_pre_sandbox_hook_linux.cc:461–496`). The standalone negative tests deliberately describe only the five added rules, not the entire browser sandbox. GPU policy already permits ioctl, getdents64, fd operations and related device mechanisms (`bpf_gpu_policy_linux.cc:71–104`). A compromised GPU process with the new AVD/media FDs can reach the corresponding kernel ioctl surface. This is a real added device-access consequence, accepted only for this scoped experiment; the patch does not supply an ioctl whitelist or prove the kernel's resistance to hostile requests.

**D4, dismissed: dangling ownership or unbounded metadata accumulation.** The selector owns strings/vectors and publishes rules by value; each read is limited to 4096 bytes; scan loops are bounded. realpath allocation is freed; metadata FDs are closed on EOF/error/overflow, and EINTR is retried (`apple_avd_gpu_permissions_linux.cc:131–165`). No device is opened by this selector; no retained device FD, VA object, surface, DMA allocation or teardown behavior is added. Bounded byte/node counts are not a guarantee that a syscall or repeated EINTR returns within a wall-clock deadline.

**D5, dismissed: the runtime render override cannot reach this GPU or feature name is wrong.** The actual VA wrapper honors `--render-node-override` at `vaapi_wrapper.cc:1647–1655`, and `LoadDrmFD` rejects unavailable/vgem/blocked Nvidia cases but does not reject an Asahi platform GPU (`:101–137`). Default enumeration skips non-PCI devices (`:1674–1676`), so explicit validation/selection matters. The switch is propagated by `gpu_process_host.cc:316`. The runtime feature string is `AcceleratedVideoDecoder` (`media/base/media_switches.cc:1477–1485`); the GL path returns VA-API when enabled (`media/mojo/services/gpu_mojo_media_client_linux.cc:108–115`). Disabling UseOutOfProcessVideoDecoding keeps the experiment on the inspected GPU path (`:32–42`; `media_switches.cc:1156–1167`).

**D6, dismissed at source level; full link still pending: GN/export mismatch.** The common source set includes the selector/hook and already depends on sandbox_services and media buildflags (`content/common/BUILD.gn:375–395`). The tests receive the new source and a later, initialized deps addition (`content/test/BUILD.gn:3165–3169,3419–3423`). sandbox_services owns BrokerFilePermission (`sandbox/linux/BUILD.gn:304–365`). DiscoverPermissions and NativeDeviceFileSystem are CONTENT_EXPORT; exported definitions and inline model structs match the component/noncomponent access scheme (`content/common/content_export.h:8–22`; `content/BUILD.gn:44–80`; `content/common/BUILD.gn:434–439`). Actual args/gen buildflags show ARM64, use_vaapi=true, use_v4l2_codec=false and component mode. Successful real GPU objects strengthen compile reachability, but do not establish test linking.

## TOCTOU and unresolved assumptions

- **U1, accepted scoped assumption, not atomic validation.** The second selected-node reads compare device number, filesystem/inode identity and derived topology (`apple_avd_gpu_permissions_linux.cc:190–199`). They catch observed deletion/identity changes between snapshots. They do not retain FDs, compare raw compatible contents if both still match, rescan all candidates for new ambiguity, stop ABA replacement, or bind later broker opens to the checked inode. BrokerHost opens by name with client-requested flags and does not force O_NOFOLLOW (`broker_host.cc:47–50,154`). Final /dev symlink rejection at discovery does not guarantee absence of changed ancestor symlinks later. Kernel-owned sysfs and root-controlled /dev ancestry/device names must remain trusted and stable after startup, with no hotplug/rebinding/privileged replacement during this integrated-SoC experiment. A privileged actor violating that premise is outside the claimed model. No unprivileged substitution path was established within the stated host model.
- **U2, platform-specific availability.** Fixed ranges and exact T8103 topology/driver names can intentionally reject otherwise functional future systems. Out-of-range devices are not granted; this is a fail-closed support limit. The selected snapshot must be revalidated immediately before the planned explicit renderD128 launch.
- **U3, startup behavior is larger than this selector.** Existing `VaapiWrapper::PreSandboxInitialization` loads libraries and probes supported profiles before the custom hook (`gpu_main.cc:183–193`; `vaapi_wrapper.cc:3361–3396`). Default-off *added permissions* do not imply that a VA-enabled build with driver environment overrides performs no pre-sandbox device probing. This is existing VA initialization behavior, not introduced selector I/O. The guarded experiment must cover browser startup, not only the two-second video segment.
- **U4, remaining runtime integration.** No linked browser or runtime OS policy test was executed here. The historical libdrm 2.4.134 source receipt maps the measured VA recreation path to `vaGetDisplayDRM -> drmGetNodeTypeFromFd -> fstat/stat(/sys/dev/char/.../device/drm)/access(render path)`; I read those actual cached source functions. The libva 2.24.1 cached source is similarly pinned. Installed driver source pin `db3014f9499694c6f186af7e023de07bd5bc3564` was read through Git for its media enumeration/uevent path, and candidate context opens were inspected. Those traces explain the five permissions, but cannot establish that no other path/import restriction will appear during real browser decoding.
- **U5, hardware and lifecycle evidence remains open.** The new permission layer does not validate DMA coherence, buffer imports/exports, displayed colors, seek/reopen, frame lifetime, reset safety, or the earlier desktop freeze cause. Generic GPU ioctls and pre-existing VA/driver behavior remain in force. The finite guard can terminate ordinary userspace; it cannot guarantee recovery from a kernel-stuck task.
- **U6, observer limits.** LinuxBackend skips /proc FD directories it cannot read; a full-state receipt is not evidence of invisible holders. The parent must use the established observer privileges/visibility and record failures as unverified. The initial runner's lease-variable assertion alone neither acquires a lease nor sets a deadline. Its JSON correctly delegates whole-boot preflight, exclusive lease and 90-second deadline to the outer invocation; that concrete invocation still needs verification.
